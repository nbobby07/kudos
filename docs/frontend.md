# Kudos Handoff Dashboard

The dashboard is a companion web interface for the shared CoShell workspace.

The root URL opens a centered monochrome Kudos landing page with the tagline "Your teammates will love you." Its **Your tasks** link opens the existing dashboard at `/tasks`. No account or authentication flow is added in this iteration.

The dashboard matches the landing page's warm off-white, charcoal, and gray palette. `public/theme.css` applies the monochrome theme across navigation, task controls, avatars, dialogs, verification states, and the checkout illustration without changing the workflows.

Run `npm start` to build the Assistant UI chat bundle and serve the app on `0.0.0.0:5173`. When launching the server directly, first run `npm run build:chat`, then `node server.js`. Port 3000 is reserved for the separate backend API scaffold. `PORT` can override the frontend port.

The sidebar has four screens: **My day**, **Team chat**, **Calendar**, and **Verification**. Standalone Shared Contract and Incoming screens have been removed. The home page centers on two side-by-side columns: the selected teammate's daily tasks and curated AI-style recommendations. On mobile they stack in reading order. Add recommendations to the plan, check off tasks, and send the completed list from the compact teammate dock below. All tasks must be complete; the server enforces this too. Task deliveries retain a self-reported checklist snapshot in shared state, but no separate incoming inbox is shown. They do not claim verification or capture a code revision.

**Add a new task** is at the bottom of the daily checklist. Its dialog accepts a required title, optional details, and optional due date/time fields. Set both deadline fields or leave both empty. Scheduled tasks automatically appear in Calendar at the entered date and local time; unscheduled custom tasks stay in the checklist without an invented calendar date. The server persists `dueDate`, `dueTime`, and `createdBy`, validates real dates and 24-hour times, and increments the plan version so new tasks participate in completion gating. Tasks synchronize live, persist across reloads, and retain entered values if saving fails. Blank titles, oversized text, invalid deadlines, and incomplete date/time pairs are rejected server-side.

`public/authors.css` gives Aryan a red identity, Noel green, and Kiran blue. The same source colors appear on profiles, checklist controls and attribution, chat recommendation labels, calendar events, and agenda times. Source names remain visible, so color is not the only cue. Teammate recommendations retain their original source color even when added to another person's checklist.

Each teammate card separates **Recommends for you** from **Their task** and preserves the existing next-step context. Example teammate recommendations automatically appear in the recipient's checklist with **Task by Noel** or equivalent attribution. Completing the checklist item updates the card's tracking state, and delivery snapshots preserve the source. These are seeded demo requests, not actual teammate submissions or AI-generated requests; a recommendation editor is not included yet. Existing checklist completion is preserved when the new example requests are introduced.

Teammate context is disclosed on hover or by activating a native details summary with keyboard or touch. Escape dismisses it, and the send action remains visible outside the details. `public/workspace.css` controls the simplified layout without changing the shared palette or backend state. The focus banner, repeated task instructions, and sidebar promotional block are removed from the home view to prioritize the two plans.

Layout references: [NN/g visual hierarchy](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/) for scale, grouping, and whitespace, and [Linear's product sections](https://linear.app/features) for separating planning from secondary context. These inform the hierarchy rather than supplying copied components.

**Team chat** is directly below My day in the sidebar. Conversations persist in shared state and update live across teammate views. Composer drafts are kept per conversation during live updates and navigation, but are not persisted across reloads. Teammates can send an ordinary message or explicitly choose **Recommend a task** with a title and explanation. Recommendation messages automatically appear in the recipient's AI panel with **Recommended by Noel** or equivalent attribution and an **Open chat** action. Adding one to the checklist preserves **Task by Noel** and the source message ID. Ordinary chat is not analyzed by an LLM; automatic semantic extraction of recommendations is not connected. As with the rest of this demo, the teammate selector is not authentication and the shared chat is not a private messaging security boundary.

The conversation thread uses `@assistant-ui/react` through a small React island in `frontend/assistant-thread.jsx`: `AssistantRuntimeProvider`, the external-store runtime, thread primitives, and message primitives render the real shared message history. Runtime roles only control layout; sender names and recommendation authors come from original message metadata, and adjacent messages are not merged. The custom recommendation composer and the rest of the dashboard remain in plain JavaScript. The React island is lazy-loaded on the chat screen, with explicit unmounting during navigation. `npm run build:chat` bundles it with esbuild into the ignored `public/generated/` directory. Assistant UI does not provide an AI model or backend; the existing server still owns messaging and persistence.

### Messaging Inbox and To-Dos

Opening Team chat now shows a conversation inbox: the other two teammates' DMs plus **Kiran + Noel**, a group containing Aryan, Kiran, and Noel. Message previews and unread counts update live. On mobile, choosing a conversation opens its thread; **Back to all messages** returns to the list. Group messages preserve each sender's identity and group recommendations appear in each recipient's AI panel.

New incoming DMs and group messages show small bottom-right in-app notifications with the sender, a short preview, **View message**, and a dismiss button. View message opens the correct conversation. The initial shared-state snapshot establishes a baseline rather than replaying historical alerts; subsequent updates are deduplicated by message ID. Own messages and the conversation currently being read in a visible, focused window do not trigger alerts. Unfocused/background conversations are not marked read until the user returns. Notifications remain until dismissed or viewed, with a maximum of three on screen, and are cleared when switching the demo teammate identity. These are notifications inside the open Kudos page, not operating-system push notifications or alerts when the website is closed.

Received recommendation messages have an **Add to your to-do list** action below the message. One click adds the item directly to **My tasks for today**, preserving its message ID and **Task by Noel** attribution. No modal or date is required. Repeated manual additions and manual/automatic races are idempotent per recipient and message. Once added, the message shows a confirmation and **View task**.

**Auto-add task ideas** is enabled by default and can be disabled in the inbox. Explicitly marked recommendations that remain unadded after 30 seconds become unchecked tasks in the recipient's to-do list, with an **Automatically added to your to-do list** confirmation in chat. This is a visible deterministic demo rule, not LLM interpretation or a claim that the user has not read the message. **Undo** removes the automatic task and prevents the same message from being automatically added again. Task preferences, pending deadlines, undo exclusions, and tasks persist in shared state. Existing auto-save preferences and dismissals are carried forward from the earlier calendar implementation, and prior calendar entries remain intact.

Calendar opens to October 2026, with Saturday October 3 highlighted as today. Entered task deadlines take priority and are shown as **Your due date**, never replaced with example slots. Existing demo checklist tasks without deadlines still have clearly marked **Example date** slots in October, including October 3 and 9; these are presentation-only dates, not inferred commitments. Clicking a day reveals its agenda, descriptions, attribution, and actual checklist completion. Previous/next month controls make deadlines outside October accessible, and Today returns to October 3. On mobile the compact grid shows task counts and the agenda below. Previously stored legacy calendar records are left intact but are not displayed in this task-derived calendar. There is no Google/Outlook integration or external scheduling. `CHAT_AUTOSAVE_MS` overrides the task auto-add grace period; browser tests use 2000ms and the running app defaults to 30000ms.

Verification is the defined-contract handoff gate, not a general claim that the work has no bugs. Its demo includes three teammate cards, progress, findings, and a checkout illustration. The API contract remains a tab inside Verification because it defines the checks; **Edit requirements** is available there. There is no separate incoming handoff screen or acknowledgment UI. Successful runs still capture delivery data in shared state and teammates can inspect the same run under Verification. State persists in `.data/state.json`; server-sent events synchronize browser sessions. The teammate selector is a demo view switcher, not authentication. Lists persist until edited; there is no automatic daily reset yet.

Verification is explicitly simulated. There are no real repository snapshots, browser checks, screenshots, AI evaluations, or Freestyle calls yet. The frontend's `/api/*` routes support the interactive demo only; they are not the backend submission API.

For the demo, click **Verify & Send to Noel** to see the declined-payment failure, enable the **Demo scenario** switch, and verify again. Open another browser session as Noel and use Verification to see the shared run.

Run `npx playwright test` for the dashboard tests. They use a separate process on an automatically selected free loopback port and temporary state, leaving the shared demo untouched. Use `RELAY_TEST_PORT` only when an explicit unused test port is needed. Browser contexts inherit the same base URL, including touch tests. Tests cover blocked delivery, live updates, the fixed scenario, contract editing inside Verification, overflow at 375px, recommendations, persistence, completion gating, chat, notifications, and the four-item sidebar and October demo calendar.

The next integration should replace the simulation with the backend's submission/status flow through a trusted server-side adapter. Keep backend credentials out of the browser. Preserve immutable revision and contract snapshots and treat execution errors as unverified.
